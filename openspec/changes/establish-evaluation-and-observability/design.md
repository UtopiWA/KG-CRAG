# Design

## Context

变更动机见 [proposal.md](./proposal.md)。当前 `evaluation/` 下的 Dense、Hybrid、Graph、纠错和 grounded evaluator 已能生成各自的严格报告，但题目 schema、运行身份、检查点目录和指标分母并不统一；`observability/` 仍是预留包。`TraceEvent v1` 已被工作流状态和既有产物引用，直接修改其必填字段会破坏兼容性。

本设计受以下约束：复用现有 Evidence、facet、预算、回答与 Provider 契约；默认测试不得联网；数据和报告可提交但 PDF、缓存、日志和数据库卷不可提交；正式数据仅 60～80 题，且全部策略不得批量调用 LLM。

## Goals / Non-Goals

**Goals:**

- 在不重写现有检索与回答实现的前提下，提供一种统一题目、策略观察、指标和报告模型。
- 将“facet 覆盖是否提升、是否从首次失败恢复、代价是多少”固化为逐题可复核的实验链路。
- 让中断重启、身份漂移、题目失败和可选在线调用具有一致且可测试的语义。
- 保留 `TraceEvent v1` 读取能力，同时让新评测事件携带运行与题目关联、阶段状态和资源计数。

**Non-Goals:**

- 不把已有 evaluator 合并成一个大型实现，也不改变 Dense、Sparse、Graph、Web 或 Agent 的线上决策。
- 不引入实验跟踪 SaaS、分布式任务队列、GPU Judge 或新的数据库。
- 不在 runner 内实现自动调参、自动选 Prompt 或基于测试集重新选择策略。
- 不追求通用基准平台；公共契约只覆盖本项目的冻结科研问答实验。

## Decisions

### 1. 采用“统一外层 + 现有策略适配器”，不重写 evaluator

新增评测领域模型承载数据集、运行身份、阶段结果、逐题结果和报告。三个核心策略适配器分别调用固定 Hybrid、问题类型路由和 facet 纠错的现有入口，并把结果投影为统一的 `StrategyObservation`：排序 Evidence、facet 前后覆盖、充分性判断、动作/路由/停止、回答引用、资源用量和错误。适配器不得改变原策略参数或吞掉原始失败。

runner 按 `validate -> retrieve -> assess -> answer(optional) -> judge(optional) -> aggregate -> publish` 执行；每一阶段只消费前一阶段的已发布公共产物。这样可以复用迭代 2～6 的缓存和检查点，又避免把不同策略强行塞进相同内部类层次。

曾考虑直接扩展每个现有报告并在末尾拼表，但该方案仍会保留多套身份、分母与失败语义，无法可靠下钻，因此放弃。

### 2. 统一数据由清单、题目和标注指南组成

`data/evaluation/unified/` 保存版本化清单、开发/测试题目和中文标注指南。公共模型至少表达：

- 数据集版本、schema 版本、划分、内容哈希、题目计数和来源语料版本；
- 稳定问题 ID、规范化问题、类型、答案要点、知识充分性和压力类型；
- 稳定 facet ID、必需性、满足条件、目标 Evidence ID；
- graded relevant Evidence 与一个或多个最小充分 Evidence 集；
- `leakage_group_id` 与答案来源组，用于显式绑定改写题和共享答案来源。

题目从现有小型评测 fixture 迁移候选中选取，但迁移脚本的结果必须人工复核后才可进入冻结清单。泄漏检查同时使用规范化文本完全匹配、确定性 token 相似度阈值、人工 `leakage_group_id` 和答案来源组；不为此加载 embedding 模型。清单哈希覆盖排序规范化后的全部题目和标注，不能仅哈希文件路径或修改时间。

选择单一统一文件曾被考虑，但独立清单便于在不暴露测试题内容时先完成身份和规模校验，也便于将标注规则与机器数据分开审阅。

### 3. 测试集以版本锁和不可覆盖运行记录封存

默认 CLI 只允许 `dev`。正式测试需要 `--split test --confirm-test-run`，且运行身份必须引用已发布的开发集选择记录，证明策略、配置、阈值、Prompt 和模型已冻结。每个冻结测试数据集版本只允许一个正式运行目录和锁记录；参数变化不能绕过该锁。需要纠正数据时必须发布新数据集版本，并在文档中说明旧结果失效原因。

参数搜索、策略选择、Prompt 选择和未冻结身份与 test 模式互斥。runner 先验证门禁再读取测试题正文，减少误用。此机制防止项目流程中的意外重跑，但不声称能抵御具有文件系统写权限的恶意篡改；Git 历史和产物哈希用于审计。

### 4. 运行身份采用全量内容地址，清单与检查点分离

统一 `EvaluationRunIdentity` 对规范化后的数据集/划分、语料、Evidence、Dense/Sparse/Graph 索引、评测配置、随机种子、策略、模型、Prompt、指标和 Judge 版本哈希。运行目录以身份哈希命名，`run-manifest.json` 记录预算、状态、阶段、逐题检查点路径和产物哈希。

每题每阶段写独立临时文件，校验后原子替换；清单只有在对应产物发布成功后才前移。恢复时逐项校验身份和内容哈希，损坏项按失败策略重算，身份不兼容则整体拒绝复用。在线调用的内容寻址缓存独立于运行检查点，缓存键还包括 Provider、模型、Prompt 和输入哈希，避免恢复机制误当成跨版本缓存。

曾考虑复用纠错或回答专用 `RunManifest`，但它们的身份字段和阶段枚举不能覆盖多策略评测；保留它们并由统一清单引用更清晰。

### 5. 新增 Trace v2，而不是原地扩充 v1

保留现有 `TraceEvent` 作为 v1。新增严格的 `EvaluationTraceEvent` v2，包含 `trace_id`、`run_id`、可选 `question_id`、单调 `sequence`、受控 `phase`、事件名、状态、UTC 时间、有界标量明细和结构化资源增量。题目阶段事件必须含 `question_id`，运行级开始/结束事件可以为空。写入器统一执行事件数、键数、字符串长度和敏感键检查。

读取层接受 v1/v2 的判别联合。v1 适配到只读规范视图时保留 `source_schema_version=v1`，不存在的运行/问题/资源字段保持 `None`，不猜测、不回写原文件。新 runner 只写 v2，现有工作流仍可继续写 v1，后续迭代再按需迁移。

原地给 v1 增加必填字段会使历史 JSON 和当前工作流验证失败；让字段全部可选又会削弱新评测契约，因此采用并行版本。

### 6. 指标核心是纯函数，并显式携带适用性和分母

统一指标模块只接收已验证的题目与 `StrategyObservation`，不调用 Retriever、LLM 或数据库。每个指标返回数值或 `not_applicable`、分子、分母和纳入的 question ID；报告聚合层按总体、问题类型和压力类型生成切片。排名指标复用并统一现有 Recall/MRR/nDCG 公式，graded relevance 用于 nDCG，最小充分集与 facet 标注用于覆盖和充分性指标。

首次失败恢复要求同题的初始状态不充分且纠错后达到标注的最小充分条件；无效纠错指消耗动作/调用但必需 facet 覆盖未增加且未解决冲突。单位成本收益同时报告收益、估算成本和比值；成本为零时比值标记为不适用，而不是无穷大。所有失败题留在总样本中，失败原因另行切片，禁止成功样本过滤。

指标通过手算 fixture 覆盖正常、零分母、重复 Evidence、失败、部分 facet、冲突和恢复场景，避免用同一实现生成期望值。

### 7. 回答质量采用规则/人工优先，Judge 是有界附加信号

答案要点匹配、引用 ID 存在性、引用位置和声明—证据关联先由确定性检查计算；人工复核文件保存题目、评审版本、结论和备注。Judge 通过已有 LLM Provider 的新窄 Protocol 接入，只返回严格结构化评分与理由标签，不保存完整推理。

Judge CLI 同时要求 `--with-judge`、`--confirm-budget`、入选策略记录和 `judge_max_answers <= 50`。调用前预估上限，调用后记录实际 Token/延迟/成本；失败结果也计费并缓存。Judge 分数单独展示，并与人工子集计算一致率，不并入真值或自动改变策略。

曾考虑对三种策略全部生成回答并交叉 Judge，但这会把主要开销放在并非核心贡献的生成环节，也放大 Judge 偏差，故只允许一个入选系统。

### 8. 配置给出保守默认值与不可放宽的安全上限

`configs/evaluation.yaml` 增加统一评测段，包含路径、切分、策略、Top-K、相似度阈值、逐题/全局调用与循环、Token、超时、成本、Judge 和 Trace 上限。用户配置可以收紧上限；绝对题数 100、Judge 回答数 50 和测试集单次运行由代码常量二次约束，不能只靠 YAML 放宽。

默认 Provider 均为 deterministic/recorded，`online=false`、`with_judge=false`。真实 LLM、Web、Qdrant 或 Neo4j 适配器只能在显式集成路径构造；单元测试通过会在网络调用时失败的替身验证这一边界。真实服务健康检查不通过时，仅相应阶段失败，不修改已完成的离线报告。

### 9. 报告只保存可验证引用，不复制大段内容

逐题记录引用 Evidence ID、facet ID、claim/citation ID、Trace 序号和产物哈希；只保留用于诊断的枚举、计数、分数和受限短文本，不复制 Evidence 正文、Prompt 或 Provider 原始响应。汇总项保存组成样本 ID，因此能够从任意均值或比率回溯分子和分母。

最终目录包含运行清单、逐题阶段产物、统一报告、失败清单和可选人工/Judge 对照；报告先完整验证再原子发布。终端摘要只显示运行身份、规模、关键指标、失败数与产物路径，不输出测试题或敏感内容。

## Risks / Trade-offs

- [60～80 题的 facet 与最小充分集标注成本较高] → 优先迁移已有 fixture，使用校验器和标注指南减少机械工作，但所有迁移结果必须人工复核。
- [确定性 token 相似度可能漏掉语义改写] → 结合人工泄漏组和答案来源组；不引入新的 embedding 下载与磁盘占用。
- [多策略统一会掩盖策略特有信息] → 统一层只规定公共观察，原始策略产物以哈希引用保留，策略特有字段不硬塞进汇总。
- [v1/v2 并存增加模型数量] → 仅新 runner 写 v2，读取处使用单一判别入口，并提供 schema 快照与兼容 fixture。
- [本地“只运行一次”不能抵抗恶意删除锁文件] → 以不可覆盖目录、Git 记录和内容哈希提供研究流程审计，不将其描述为安全边界。
- [失败计入固定分母会降低表面分数] → 同时报告失败切片与适用性，保证不同策略比较真实且可解释。
- [Judge 存在偏差且价格可能变化] → Judge 独立展示、人工抽检、版本/成本固化，并由 50 条硬上限控制风险。
- [逐题 Trace 和检查点增加磁盘占用] → 只保存标量、ID 和哈希，设置事件/字段上限；缓存和运行产物仍按既有忽略规则不提交 Git。

## Migration Plan

1. 先增加评测/Trace v2 模型、schema 快照和 v1 兼容读取，不切换任何现有 evaluator。
2. 增加统一数据校验器和标注指南，从现有 fixture 生成候选后人工复核，冻结新数据集版本与划分。
3. 增加策略适配器、纯指标和离线 runner；用小型 fixture 验证检查点、失败分母和下钻链路。
4. 先在开发集运行零 LLM 检索/覆盖矩阵，冻结入选系统与配置；仅在显式选择后验证回答/Judge 路径。
5. 完成开发集验收后再创建测试集锁并运行一次正式评测；更新 README、实验文档、schema 导出和 `PROJECT_MAP.md`。

若实施阶段需回滚，保留新增数据和产物但停止统一 CLI；既有 evaluator 与 `TraceEvent v1` 未被替换，可继续独立运行。尚未发布的临时文件可安全忽略，已发布报告按 schema 版本继续读取。
